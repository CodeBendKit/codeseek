# MTEB(Code, v1) × codeseek end-to-end evaluation suite

Measures codeseek's **code retrieval** on an [MTEB(Code, v1)](https://huggingface.co/datasets/mteb/CodeSearchNetRetrieval)-style
`nDCG@10` protocol, driven entirely from the command line against the real `codeseek` binary. The whole suite
uses only the Python standard library, and every artifact is written under `--workdir` (default
`/tmp/mtebcode-eval`), so **the repository is never polluted**.

The benchmark is **101 tasks**: **100** shards cut from `mteb/CodeSearchNetRetrieval` (`go` 34 shards, `java` 33,
`python` 33 — `CodeSearchNetRetrieval-<lang>-s01` … `s34`) plus **CosQA** as the 101st task. Each language
contributes its full 1,000-document code corpus and its 1,000 queries, sliced into disjoint contiguous shards of
~30 queries, so the 100 shards together cover all **3,000** queries — and all shards of one language **share one
corpus directory**, i.e. one `codeseek init` (3 corpora in total). CosQA adds **40** queries over its own
300-document pool, which brings the archived batch to **3,040** queries and **3,300** indexed documents.

> **Primary metric: `nDCG@10`.** The overall score is the **arithmetic mean of the per-task means**
> (MTEB `Mean(Task)`), not a pooled mean over queries, so CosQA (40 queries) cannot outvote a 30-query shard.
> **No LLM takes part in scoring**: relevance comes from the dataset's `qrels`, and the metrics are closed-form.

## 1. Pipeline

```
   ┌──────────────────────────────────────────────────────────────────────────────────────┐
   │ datasets-server JSON REST API   /rows?dataset=…&config=…&split=…&offset=…             │
   │   (or the local HF parquet cache when the API answers 429/500)                        │
   └───────────────────────────────────┬──────────────────────────────────────────────────┘
                                       ▼
   ┌──────────────────────────────────────────────────────────────────────────────────────┐
   │ data  ── page cache under <workdir>/cache/   (100 rows per page, retries with backoff)│
   │      ── TaskSpec registry: which tasks/languages are usable, and why the rest are not│
   └───────────────────────────────────┬──────────────────────────────────────────────────┘
                                       ▼
   ┌──────────────────────────────────────────────────────────────────────────────────────┐
   │ prepare ─ deterministic sampling (seed)                                              │
   │   1. keep every qrels row with score > 0                                             │
   │   2. shard: the language's 1,000 queries, sorted, split contiguously into N disjoint │
   │      slices (go 34 / java 33 / python 33) -> ~30 queries per shard, union = all       │
   │   3. build the pool:  gold documents ∪ random distractors  -> `--corpus-size` docs    │
   │      a `full_corpus` task materializes the whole 1,000-doc corpus instead, so every    │
   │      shard of one language sees byte-identical docs/ + docmap.json (1 index / lang)   │
   │   4. materialize each document as a real file (extension from the language)          │
   │      + docmap.json  {relative path -> doc_id}                                        │
   │   5. `git init` in every corpus dir   (hard prerequisite for `codeseek init`)         │
   │   6. write tasks.jsonl + meta.json (incl. sampling_fingerprint)                      │
   └───────────────────────────────────┬──────────────────────────────────────────────────┘
                                       ▼
   ┌──────────────────────────────────────────────────────────────────────────────────────┐
   │ run ─ 1. serial:     codeseek init            (once per corpus, resumable)            │
   │     ─ 2. concurrent: codeseek search --json --limit K -- "<query text>"   (cwd=corpus)   │
   │           adapter.parse_json_tolerant -> results                                      │
   │           write raw/<task_id>.json            (resumable runs)                        │
   │     ─ 3. score:  resolve doc_ids -> dedup keep-first -> nDCG@10 / recall / MRR        │
   │     ─ 4. report: report.json + report.md                                              │
   └───────────────────────────────────┬──────────────────────────────────────────────────┘
                                       ▼
              <workdir>/report.json   (machine-readable: meta / aggregate / per_query / failure_top)
              <workdir>/report.md     (human-readable, English, generated by render_markdown())

   score ──► re-reads raw/*.json only (new --k / --limit, no retrieval re-run)
```

## 2. Prerequisites

| dependency | notes |
| --- | --- |
| Python >= 3.10 | **standard library only, no third-party packages**; type annotations use the `X \| None` syntax |
| codeseek binary | `cargo build --release --manifest-path rust-core/Cargo.toml` -> `rust-core/target/release/codeseek`; resolved from `--codeseek-bin`, then `CODESEEK_BIN`, then the repo default |
| network access through a proxy | a direct connection to HuggingFace `datasets-server` is **not** reachable from this machine. The client reads `https_proxy` / `http_proxy`, or take `prepare --proxy http://127.0.0.1:7897` |
| embedding token (**decides whether scores are comparable**) | semantic retrieval runs in `hybrid` mode only when `embedding.api_token` in `~/.codeseek/config.json` is non-empty. When it is empty codeseek degrades to `name_fallback` (function-name substring matching, no `code_block`) and the score is **not comparable** with a hybrid run |
| git | `prepare` runs `git init` in every corpus directory; `codeseek init` fails with `No project found` outside a git repository |
| **`index.hybrid.cutoff.enabled = false`** | **required for the archived result.** With the default (`true`) the three-gate adaptive cutoff trims a short query to about **one** result, which collapses `nDCG@10`, `recall@10` and `MRR@10` onto the same number and turns most queries into `unknown_empty`. There is **no CLI flag and no environment variable**: write `{"index": {"hybrid": {"cutoff": {"enabled": false}}}}` into `~/.codeseek/config.json` (merge, never overwrite — the `embedding` section must survive) and restore the file afterwards |

## 3. The four commands

```bash
cd evals/mtebcode

# 0. offline self-test: nDCG arithmetic / tolerant JSON parsing / doc_id mapping / end-to-end report
#    (no network, no codeseek binary, no dataset)
python3 -m mtebcode_eval selftest

# 1. prepare: fetch + shard + materialize + git init  (`--tasks csn` = all 100 CSN shards)
#    The CSN shards ignore --limit-queries / --corpus-size: each shard takes its own contiguous
#    slice of the language's 1,000 queries and the language's whole 1,000-document corpus.
python3 -m mtebcode_eval prepare \
  --workdir /tmp/mtebcode-csn \
  --tasks csn \
  --seed 42 \
  --proxy http://127.0.0.1:7897

# 2. run: serial init (3 corpora) + concurrent search (3,000 queries) + scoring + report
python3 -m mtebcode_eval run \
  --workdir /tmp/mtebcode-csn \
  --limit 20 \
  --k 10 \
  --concurrency 4

# 3. score: re-compute the metrics only (new --k, no retrieval re-run)
python3 -m mtebcode_eval score --workdir /tmp/mtebcode-csn --limit 20 --k 10
```

| command | flag | meaning |
| --- | --- | --- |
| `prepare` | `--workdir` | where `cache/`, `corpora/`, `tasks.jsonl`, `meta.json` land |
| | `--tasks` | comma-separated task names from the `TaskSpec` registry; the alias `csn` expands to all 100 CSN shards |
| | `--limit-queries` | queries per task (default 30; `0` = all); a `TaskSpec.query_quota` overrides it per task — the CSN shards pin it to `0` so every shard always slices the full 1,000 queries |
| | `--corpus-size` | documents in the pool per task (default 300); **ignored by `full_corpus` tasks** (the CSN shards materialize their whole 1,000-doc corpus so all shards of a language can share one index) |
| | `--seed` | sampling seed (default 42; the resulting `sampling_fingerprint` is recorded in `meta.json`) |
| | `--proxy` | download proxy (falls back to `https_proxy`) |
| | `--parquet-cache` | local HF hub directory; a cached `(config, split)` is read from disk instead of the network |
| | `--cache-only` | pure offline: fail instead of fetching any missing page |
| | `--rate-limit` / `--retries` | sleep between real requests (default 0.15 s) / per-page retries (default 4) |
| | `--force` | rewrite corpus files and `docmap.json` |
| `run` | `--limit` | `codeseek search --limit` (default 20); also the `k` of the `recall@k` column |
| | `--k` | `k` of the primary `nDCG@k` metric (default 10) |
| | `--concurrency` | search worker threads (default 4) |
| | `--timeout` / `--init-timeout` | per-query search timeout (180 s) / per-corpus init timeout (1800 s) |
| | `--force` | ignore existing `raw/` results and re-run retrieval |
| | `--auto-build` | run `cargo build --release` when the binary is missing (only when explicitly asked) |
| `score` | `--limit` / `--k` | same semantics as `run`, but no retrieval is performed |
| | `--limit-queries` | score at most N queries per task (0 = all) |

## 4. Evaluation protocol (rule by rule)

1. **Data access.** Everything is pulled from the **datasets-server JSON REST API**
   (`/rows?dataset=…&config=…&split=…&offset=…&length=…`), **100 rows per page** — that is the server-side
   maximum, so 1,000 corpus rows cost 10 requests. Every real request is followed by a `--rate-limit` sleep
   (default 0.15 s) and a failing page is retried up to `--retries` times with exponential backoff
   (1 s, 2 s, 4 s …). When a local HF parquet cache holds the `(config, split)` pair it is read **from disk**
   instead, which is the practical answer to `429 Too Many Requests`.
   **The on-disk page cache is keyed by `(offset, length)`, and that is load-bearing.** `probe_id_scheme` reads
   the same offsets with `length = 1`; if the cache ignored `length`, `iter_rows` would get that 1-row page back
   for the full page, advance `offset += 100`, and silently drop 99 rows. That is exactly the historical bug that
   made each CodeSearchNet language yield 901 instead of 1,000 queries (missing `501..599`, because
   `num_rows // 2 == 500`): `rows()` therefore both keys on `length` **and** re-fetches any cached page that is
   shorter than requested without being the last page.
2. **Task screening comes before sampling.** A task is only usable when three things hold: the queries are short
   enough to be a realistic search query, the corpus text is actually code, and the corpus is materializable
   into an extension codeseek indexes. The current task set is the **101-task
   `mteb/CodeSearchNetRetrieval` batch** (go / java / python shards + CosQA): its corpus rows are real source files
   (docstrings moved to the query side) and its queries are stripped natural-language docstrings. The CoIR
   tasks that were screened out stay in the registry with an explicit `excluded_reason` — `CodeFeedbackST`
   (median query 540 chars), `CodeTransOceanContest` (547), `StackOverflowQA` (883), `CodeTransOceanDL` (1,211),
   `AppsRetrieval` (1,316), `CodeFeedbackMT` (3,571) for query length, and `SyntheticText2SQL` because a `.sql`
   corpus is outside codeseek's extension whitelist. `ruby` is excluded too: `.rb` is not in that whitelist, so
   its corpus would index as 0 files; `javascript` and `php` are excluded by requirement. The full screening
   table is Section 2.4 of [`results/README.md`](results/README.md).
3. **Sampling is deterministic.** `--seed` fixes which distractors are taken, the shard slice is a pure
   function of the sorted query list, and the resulting `sampling_fingerprint` (a hash of the task list, seed,
   `corpus-size` and `--limit-queries`) is written to `meta.json`, so two runs with the same fingerprint are
   the same queries and the same pools.
4. **Pooling.** For a classic task the corpus is **not** the full dataset: it is `gold documents ∪ random
   distractors` up to `--corpus-size` (300). If the number of gold documents alone exceeds `--corpus-size`, the
   list is **truncated** and a warning is appended to `meta.prepare_warnings` ("some queries lost their gold
   document, the metric will read low"). If a query's gold documents all fall outside the pool, the query is
   recorded as skipped instead of silently scoring 0. **`full_corpus` tasks (all 100 CSN shards) bypass pooling
   entirely**: the whole 1,000-document corpus is materialized in the corpus' original order, which is what makes
   the shards of one language share a single index (`--corpus-size` is ignored, and `n_pool_docs_target` in
   `meta.json` records the real pool size).
5. **Materialization.** Each pooled document is written as a real file whose extension comes from the task's
   language (`.py`, `.go`, `.java`, `.ts`, `.sql`, `.txt`), because codeseek's indexer only picks up
   `cpp/cc/cxx/c++/c/h/hpp/hxx/hh/inl/inc/tpp/tpl/py/py3/pyx/java/rs/ts/tsx/js/jsx/go`
   (`rust-core/src/codegraph/parser.rs`, `is_supported_file`). The file name is
   `<dataset-stem>_<sha1(doc_id)[:8]><ext>` — the hash prefix keeps two documents with the same stem from
   colliding — and `docmap.json` records `{relative POSIX path -> doc_id}` for the reverse mapping. `.sql` and
   `.txt` files are **not** given a title comment (those corpora must stay byte-exact); code files may carry one,
   but the CSN shards set `code_like = False` because their `title` field is always the empty string.
   **Primary keys are read as `row["id"] or row["_id"]`**: the official MTEB datasets use `id` (CoIR uses
   `_id`), and `qrels` accept both `query-id`/`corpus-id` and `query_id`/`corpus_id`. `TaskSpec.diff_postimage`
   (a unified-diff → post-image normaliser for corpora that ship patches instead of source) is kept together with
   its unit tests, but **no registered task uses it any more**.
6. **The search call.** Exactly one process per query:
   `[binary, "search", "--json", "--limit", str(K), "--", query_text]` with `cwd = <corpus_dir>` and **no shell**
   (an argv list, `shell=False`), so a query containing quotes or `$` cannot be reinterpreted. The query goes
   **after `--`** because it is a positional argument: CodeSearchNet contains queries that start with `-`
   (a whole line of `-----`), which clap would otherwise reject as an unknown flag with exit code 2
   (`error: unexpected argument '-----…' found`). A non-zero exit, a timeout, or unparsable JSON is recorded
   as an error for that query and the run continues.
7. **Result -> `doc_id`, four levels of fallback**, then dedup. For each result element:
   (1) `file_path` / `path`, normalised to a POSIX path **relative to `corpus_dir`** (absolute paths, `./`
   prefixes and paths already containing `corpus_dir` are all handled), is looked up in `docmap`;
   (2) otherwise the `basename` is matched against the docmap keys; (3) otherwise `name` / `symbol_name` is
   compared against the `doc_id` set; (4) if all three fail the element is **dropped and counted in
   `n_unmapped`**. Survivors are then **deduplicated keeping the first occurrence**: codeseek may return several
   chunks of the same file, and without this step one document could fill the whole Top-K and nDCG would be
   badly overestimated.
8. **nDCG@10.**
   `DCG@k = Σ_{i=0}^{k-1} (2^{rel_i} − 1) / log2(i + 2)`, normalised by `IDCG@k` (the same sum over the ideal,
   descending ordering of the graded qrels): `nDCG@k = DCG@k / IDCG@k`. A query with **no positive qrels**
   returns `None` and is **skipped** — it is never folded into the mean as a `0.0`, which matches MTEB's own
   aggregation. `recall@k` and `MRR@k` use the same ranked list; `recall@k` additionally uses the real search
   budget (`--limit`, i.e. 20 in the archived batch) while `nDCG` / `MRR` stay at `k = 10`.
9. **Aggregation.** A task's score is the **mean over its scorable queries**; the overall score is the
   **arithmetic mean of the per-task means** — MTEB's `Mean(Task)`, taken over the 100 shard means.
   `aggregate.aggregation` is written into the report as `mean_of_task_means` so nobody can misread it as a
   pooled mean. A single broken query becomes a traceable record and **does not abort** the aggregation.
   `aggregate.by_language` adds a **per-language layer** (go / java / python): `n_tasks` (shards of that
   language) plus `task_means` / `mean_of_task_means`, again the arithmetic mean of that language's shard means.
   It is an extra view only — the overall number keeps its `Mean(Task)` semantics.
10. **No LLM involved.** No generative model scores anything anywhere in the pipeline: relevance is the dataset's
    `qrels`, and every metric is closed-form arithmetic over the returned ranking.

## 5. Known limitations and risks

- **Pooling distorts difficulty (classic tasks only).** A 300-document pool is far smaller than the real corpus
  (the Hub reports **20,604** corpus rows for CosQA), so absolute recall there is **systematically higher** than
  on the full corpus. The 100 CSN shards do **not** pool — they index the whole 1,000-document corpus of their
  language — but that corpus is itself a 1,000-row sample of CodeSearchNet. Numbers are comparable across
  batches of this suite, **never** against the MTEB leaderboard or another harness.
- **A single gold document per query makes nDCG@10 and MRR@10 monotone transforms of the same rank**
  (`nDCG = 1/log2(rank+1)`, `MRR = 1/rank`). `mteb/CodeSearchNetRetrieval`'s qrels are exactly 1 query ↔ 1
  document with `score = 1`, so the only independent signal is **recall**; decoupling ordering quality would
  need multi-gold tasks or graded relevance.
- **`recall@10` and `recall@20` are close in the archived batch** (0.9720 vs 0.9819), i.e. gold documents almost
  never sit in positions 11–20. The budget of 20 is essentially sufficient, but the protocol barely measures
  anything about positions 11–20, so "ranked 11th" and "never retrieved" stay hard to tell apart.
- **Only go / java / python are covered.** `javascript` and `php` are excluded by requirement; `ruby` is excluded
  because `.rb` is not in codeseek's extension whitelist, so its corpus would index as 0 files. Every config of
  `mteb/CodeSearchNetRetrieval` exposes a single `test` split — there is no train/valid to fall back on.
- **Shards are unequal by construction.** 1,000 queries cannot be split evenly into 34 or 33 slices: the go
  shards hold 29–30 queries and the java / python shards 30–31. Because the overall score is `Mean(Task)` over
  shards (not over queries), a language with more shards does not gain weight — but a single-figure difference
  between two shards is within one query's worth of noise.
- **The reranker is an uncontrolled variable**: `enabled` with `top_n = 5`, but
  `derived_top_n = max(top_n, final_budget) = 20`, so its effect on short queries was not measured.
- **Every result is bound to its cutoff configuration.** With the default `index.hybrid.cutoff.enabled = true`, the
  three-gate adaptive cutoff trims short queries to about one result, which collapses `nDCG@10`, `recall@10` and
  `MRR@10` onto the same value and turns most queries into `unknown_empty`; the archived numbers
  (**0.9182**, `unknown_empty = 0`, `mean_returned = 20.00`) require the cutoff **disabled**. A result without
  its cutoff state is not interpretable.
- **Very long queries have a practical usability ceiling**: a screening probe on one AppsRetrieval query
  (1,316-character median family) returned `[]` for the full text and 3 results once truncated to its
  152-character first line. That is a product-side defect, and it is why long-query tasks are excluded rather
  than merely scoring low.
- **The `name_fallback` mode silently changes what is measured**: without an embedding token the search degrades
  to function-name substring matching and every result lacks a `code_block`. The report opens with a warning and
  `meta.mode_counts.name_fallback` counts the affected queries.

## 7. Resumable runs and troubleshooting

- **Resuming**: if `raw/<task_id>.json` already exists the search is skipped; `--force` re-runs everything.
  `prepare` skips the network for any page already in `cache/`, and `--force` rewrites the corpus.
- **One query failing never aborts the run**: a non-zero exit, a timeout or unparsable output becomes
  `raw.error` (first 500 characters of stdout/stderr) and the aggregation carries on.
- **One corpus failing to init** marks every query of that corpus as failed (`error="init_failed: ..."`) and the
  remaining corpora still run; `init_failures` is written into `meta`.
- **Many `unknown_empty` in the report?** Check in this order: (1) **is the adaptive cutoff still enabled?** this is
  by far the most common cause — `mean_returned ≈ 1` with `unknown_empty` in the dozens is the signature;
  (2) does `cd <corpus> && codeseek init && codeseek search --json --limit 20 -- "…"` return anything by hand
  (index not built, binary mismatch); (3) are the queries extremely long — the retrieval backend degrades on
  very long input; (4) did `docmap.json` get written — a missing or empty docmap is reported in `per_query.error`.
- **`429 Too Many Requests` from `/rows`**: lower the request rate with a larger `--rate-limit`, or point
  `--parquet-cache` at a populated `~/.cache/huggingface/hub` so the rows can be read from disk.
  **`500` from `/rows`**: that config's parquet is unreadable by the datasets server — one of the historical
  reasons `ruby` was ruled out (its `.rb` corpus sits outside the indexer whitelist anyway).
- **Binary not found**: the error message prints the exact
  `cargo build --release --manifest-path rust-core/Cargo.toml` command; `--auto-build` builds it for you.
- **`--cache-only`** turns any cache miss into an immediate error, which is the reliable way to prove a
  reproduction is fully offline.

## 8. Measured results

**The archived primary result is the 2026-11-16 batch: mean nDCG@10 = 0.9182** — **101 tasks / 3,040 queries**
(100 `CodeSearchNetRetrieval` shards + CosQA), **3,300** documents indexed, `k = 10`, `search_limit = 20`,
`seed = 42`, `concurrency = 8`, retrieval mode `hybrid` on **100%** of the queries, and
**`index.hybrid.cutoff.enabled = false`**:

| scope | tasks | queries | nDCG@10 | recall@10 | MRR@10 | recall@20 |
| --- | --- | --- | --- | --- | --- | --- |
| **Overall `Mean(Task)`** | **101** | **3040** | **0.9182** | **0.9720** | **0.9004** | **0.9819** |
| CodeSearchNetRetrieval (100 shards) | 100 | 3000 | 0.9178 | — | — | — |
| CosQA | 1 | 40 | 0.9598 | 1.0000 | 0.9458 | 1.0000 |

| language | shards | nDCG@10 | recall@10 | MRR@10 | queries |
| --- | --- | --- | --- | --- | --- |
| go | 34 | 0.9448 | 0.9870 | 0.9306 | 1000/1000 |
| java | 33 | 0.9101 | 0.9607 | 0.8935 | 1000/1000 |
| python (incl. CosQA) | 34 | 0.8994 | 0.9681 | 0.8769 | 1040/1040 |

- Report and per-query detail: [`results/README.md`](results/README.md), with
  [`results/2026-11-16-report.md`](results/2026-11-16-report.md) and
  [`results/2026-11-16-report.json`](results/2026-11-16-report.json) (binary under test `sha256` prefix
  `d14604f6583c55c5`).
- **Both tables use the `mean_of_task_means` scope**: a language row is the mean of that language's per-shard task
  means, so 34 shards cannot outvote 33. The query-level scope also exists in the JSON (`go 0.944746 /
  java 0.910439 / python 0.899749`) and is **not** used here. CosQA is folded into `python`, which is why that row
  carries 1040 queries.
- **Failure decomposition**: `1 − recall@10 = 0.0280` (recall loss) against `recall@10 − nDCG@10 = 0.0538`
  (ordering loss), and `0.0280 + 0.0538 = 0.0818 = 1 − 0.9182`. **Ordering loss is now about twice the recall
  loss**, i.e. the bottleneck has moved from candidate generation to rank-1 precision.
- **Shard spread**: worst `python-s22` 0.7523, then `python-s30` 0.7949 and `java-s27` 0.7971; four shards tie at
  `1.0000` (`go-s07`, `go-s26`, `go-s33`, `java-s09`). Every one of the 100 shards reports
  `mean_returned = 20.0` and `with_errors = 0`, and no shard returns an empty list. A shard holds only ~30
  queries, so a single-shard figure is noise — the aggregate is the signal.
